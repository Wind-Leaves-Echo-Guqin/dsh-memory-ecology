| 概念 | 一句话 | 现状 |
|---|---|---|
| 多生态圈 | 有边界的**栖息地**（圈）：隔离、迁徙受门约束 | ✅ 已交付（f9b5ebb：主圈常驻/副圈热挂载/两层筛选/circle_hit） |

## 1. 设计原则（三条硬约束，违反即否决）

1. **不造第三套并行存储**。本项目已吃过 `core/` vs `src/` 双线的苦（审计 04-P2-8：md5/sha1 双指纹 + gate_log schema 双轨，两线同库即一方崩）。记忆海与知识网**必须长在现有 eco.db + memories/ 树上**，新表新目录可以，新数据库不行。
2. **海里默认不进上下文**。记忆海的定位是"沉底"，预算纪律（catalog budget / pre-step 增量注入）不能被它破坏。进上下文的唯一通道是显式检索命中 + 计费记账。
3. **R4 之前不动工**。五账一形（gate/quota/distill/review/inject 账本统一形态）与 runner 零正则是知识网账目与海检索的地基；在双轨账本上叠图存储 = 把双源问题复制进新层。

## 2. 记忆海（Memory Sea）

### 2.1 概念模型

```
L1（MEMORY/USER）      —— 常驻意识：高结构、强预算、每轮可进上下文
   ↑ 门② promote / ↓ 门④ demote
目录（catalog）         —— 工作记忆：条目级结构化，按圈物化
   ↑ 门① 入库 / ↓ 挤出/降级/归档
记忆海（sea/）          —— 长时程基底：低结构、无预算压力、只有检索能唤醒
```

与「目录」构成**两级**：目录是"记得自己有什么"，海是"沉下去但还在"。归档（archive/）今天已经是半个海——它是**按文件名的**（词面 slug），海把它的取回键从"文件名"升级为"语义近邻"。

### 2.2 数据形态（长在现有树上）

- 目录：`memories/sea/<scope>/<yyyy-mm>/`，条目就是现在的 detail frontmatter 格式（**零 schema 新发明**），状态 `status: sea`（新增枚举值，与 active/dormant/archived 并列）。
- 索引：复用 sqlindex（FTS5）+ 新增 `sea_embedding` 表（eco.db 内；向量缓存的库分模型纪律沿用 memory_query.VectorCache）。**先词面后向量**：v1 只做 FTS 近邻 + hit 记账，向量列留表不填——与 `_embedding_ratio` 的 stub 姿态一致（审计 01-P3-14），避免又一次"声称已修"。
- 账本：`sea_log`（入海/唤醒/回收，五账一形后按统一账形建）。

### 2.3 进出海通道（全部走门，不新增旁路）

| 方向 | 通道 | 约束 |
|---|---|---|
| 入海 | 门④ 降级的第三个去向（现在只有 dormant/quarantine）：archive 满龄 → sea | 只降级不删除（红线：物理删除禁用），海是 archive 的语义可寻回形态 |
| 唤醒 | 检索命中海条目 → 计入 hit + 注入正文（带「来自记忆海」标记） | 唤醒 N 次后可由门②/人工提回目录（bring-sea-up，对齐 bring-back） |
| 不进上下文 | catalog 物化**永不**包含 sea 条目 | materialize 的 scope 过滤加 status 层；预算因此零增量 |

### 2.4 与多生态圈的关系

海按 scope 分目录——圈是海的"渔场"：圈间迁徙（f9b5ebb 的圈机制）不经过海；跨圈检索命中海条目同样记 circle_hit（驯化晋升的账继续记）。

## 3. 知识网（Knowledge Web）

### 3.1 概念模型

把**已经发生**的关系变成**可查询的数据**。今天这些关系散在四处：detail frontmatter 的 `superseded_by` / `evolved_from` / `merged_into`、gate_log 的 CONFLICT/MERGE 动作、distill_log 的 promote 谱系、circle_hit 的跨圈命中——它们都是"事实发生过"的单行记录，没有人能把"这条记忆的来龙去脉"一次查出来。

### 3.2 数据形态（图即存储，不是图数据库）

- 节点 = 现有 detail 条目（**不新建节点存储**；slug/fm.id 就是节点 id）。
- 边 = 新表 `rel(edge, src, dst, kind, ts, evidence)`，kind 初始四种：
  - `derived_from`（演化，吸收 evolved_from 的写入点）
  - `merged_into`（合并，吸收 merged_into 的写入点）
  - `contradicts`（矛盾，CONFLICT/SUPERSEDE 落边）
  - `corroborates`（印证，门③ 交叉印证 / occurrences 同源落边）
- 写入点**全部寄生在现有动作上**：门① MERGE 顺手写一条 merged_into、CONFLICT 顺手写 contradicts……不新增任何"需要单独跑"的建网任务（runner 零正则的纪律同样适用于网：建网不做正则扫描，只做动作旁账）。
- 查询：`memory_trace <slug>`（一个 CLI 子命令 + 插件工具）——向上游追溯来源链、向下游看影响面；Lineage 可视化从"读 frontmatter 拼图"改为"读 rel 表"（可视化与存储第一次同源）。

### 3.3 为什么这不是第三套存储

rel 表的每一行都能从账本重放（gate_log/distill_log 是它的幂等来源，fingerprint 可对账）；rel 丢了可以重建——它是**账本的物化视图**，不是第二个真相源。

## 5. 待拍板问题（交接 #9 的具体化）

1. 海的命名与位置：`memories/sea/`（本文）vs 沿用 archive/（改造它）——改造 archive 少一个目录语义，新建 sea 少一次迁移。
2. `status: sea` 新枚举 vs 沿用 `status: archived` + 位置区分——前者查询显式，后者零 schema 变更。
3. rel 表的 evidence 字段粒度：账本行号（可对账）vs 事件摘要（人读）。
4. v1 是否只要海不要网（网依赖 R4 更深）——本文倾向海网分批，v1 只做海。

## 6. 明确不做

- 不做第三套数据库 / 不引入外部图数据库 / 不引入向量数据库服务（向量只做 sqlite 表 + 本地模型，沿用 VectorCache）。
- 不做"海自动 summarize 上浮"——上浮是门②③ 的职责，海只被动唤醒。
- 不在海里存 PII 未脱敏副本（pii.mask 纪律沿用，脱敏口径统一项见审计 04-P3-1）。
