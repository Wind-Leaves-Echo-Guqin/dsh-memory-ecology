# 外部方案对照：v17「部署提示词」对我们的实际意义

> 对象：别人写的《记忆系统·部署提示词（v17 定稿）》四页 + 作者三条补充（提醒问"记忆更新了没"、成本 3–5 分/天、装完自查）。
> 我方：`dsh-memory-ecology` v3.2.2（本仓库 HEAD `c86bf54`）。
> 方法：不采信对方文档自述，也不采信我方文档自述；关键结论都在本机实跑复现过（脚本见 §7）。
> 日期：2026-10-30。

---

## 0. 一句话结论

**v17 不是竞品，是镜子。** 它用"纯提示词 + 纯文件 + 纯纪律"实现了一套和我们同构的治理骨架，
恰好把我们**自己没测到的那几个洞**照了出来 —— 其中最硬的一个是：
**我们的 L1（`MEMORY.md` / `USER.md`）没有任何模型可见的读者，门② 的"提升"对模型是零影响。**
这是本项目自己写进 `ARCHITECTURE.md` §10 的 C2「具名读者：无消费者的字段/接口 = 断链」，
被自己的代码违反了一次，而 167 条测试全绿。

## 1. v17 是什么（用我们的话翻译一遍）

| v17 的说法 | 等价于我们体系里的 |
|---|---|
| 桌面页 `AGENTS.md` 里 `<!--MEM:START-->…<!--MEM:END-->`，"每轮自动读" | **warm 档注入面**（载体是 AGENTS.md → 走宿主 `dsh-agent-instructions` 的 `user/message` 基线；**但"每轮"是它的说法，不成立**：宿主没有文件 watcher，见 §4.3） |
| 四个柜子 / 第一~第五层，`level` + `到期` | **单轴状态机 + 遗忘曲线**（门④），但层数是 5 不是 3 |
| `state.json` 是唯一真相 | **账本**（`eco.db`） |
| `新条目.jsonl` / `命中.jsonl` | **候选（pending）+ `hit` 表** |
| `待并入L1.md`、日档、总本、长期 | **L1 + 日摘要 + 会话归档 + 变更史**（后三个我们没有） |
| `nightly` 十四步 | **`gate all`**（门①→②③④） |
| 两班定时（22:05 脚本 / 22:35 模型） | **`agent/created` + `agent/turn-stopping`（零 cron）** |
| 防撞车 `nightly.lock`（含进程号，30 分钟视为死锁） | **我们缺**（见 §3.3） |
| 第 10 步「对账：账本说在 L1 但桌面页找不到 → 降一级」 | **我们缺**（见 §3.1，正是它照出的洞） |
| 人和约「永不自动删」+ 事「30 天删」 | **红线 1：代码层禁止 unlink**（比它更硬） |
| 掷骰子（3% / 1% 概率升降） | 确定性 protect + cooldown（我们） |

**结构同源到什么程度**：连踩的坑都一样 —— 它的 `export.mjs` 写着"zstd 帧魔数 28 B5 2F FD 要逐帧切"，
我们的 `measure.py` 写着"`decompress()` 只能解单帧（13MB 会话只解出 1 行），必须 `stream_reader`"。
两个互不相识的实现同时栽在同一个格式事实上 —— 这说明那条是**格式约束**，不是谁的实现选择。

## 2. 它验证了我们什么（我方判断被外部独立印证）

1. **"记忆不是存储，是治理"** —— 它通篇没有一句讲"召回更准"，全长在分层、到期、命中、退役、账本上。
   这与 `README.md` 第 15 行"这不是存更多、召回更准，是治理记忆的生死"是同一个命题。
2. **"必须物化成静态产物"** —— 它把桌面页做成文件由插件读，而不是每轮现算。我们实测"系统提示词在
   `agent/created` 后 ~10ms 装配完、子进程取数要 80ms"，结论一致。
3. **"账本要说人话"** —— 它第 14 步强制写"L1=n L2=n … 今晚并入=n"，我们做成了
   `ledger.gate_status()` 的四档判读（`dead` / `idle-spin` / `starved` / `stale`）。它靠人看，我们靠机器判。
4. **"路径不许写死"**（它："由脚本按自身位置算，不许写死盘符"）、**"原子写"**（它：先写 `.tmp` 再改名）
   —— 对应我们的 `paths.resolve_root()` 四条优先级与 `write_atomic`。
5. **"永不物理删除"** —— 它对人/约成立；我们对全部条目成立（`test_no_unlink_of_memories_anywhere` 扫源码）。

## 3. 它照出了我们什么（本轮最有价值的部分）

### 3.1 【严重】L1 写了没人读：门② 的提升对模型是零影响

v17 第 4 条"翻本子：桌面页给日期 → 只开那天的纸"、第 10 条"对账：账本说在 L1 但桌面页找不到就降级"，
都建立在同一个前提上：**写进桌面页 = 模型下轮一定会看见**。我们缺的就是这一环。

**这不是"一直如此"，是迁移造成的回归。** 翻宿主源码可以定位到断点：

| 宿主 | L1 的读者 | 证据 |
|---|---|---|
| **Hermes**（我方旧宿主） | **有**。`MemoryStore.load_from_disk()` → `format_for_system_prompt("memory"\|"user")` → 进 system prompt | `hermes-agent/agent/system_prompt.py:527-532`、`tools/memory_tool_store.py:175-192, 253, 618-621`（注释明确写着"load-time snapshot，NOT live state——保持 prefix cache 稳定"） |
| **dsh**（我方新宿主，v3.2 插件） | **无**。三个 `systemPrompt.section`（`eco:catalog` 全局 / 同名副圈 / `eco:packs`）**没有任何一个读 `MEMORY.md` 或 `USER.md`** | `plugin/index.js:457, 500, 613`；`retrieve.catalog_payload()` 数据源是 `root.items()` |

也就是说：**v3.2.0 剪断 Hermes 脐带时，把"L1 的读者"一起剪掉了，但没有补一个新的。**
旧链路是「门② 写 MEMORY.md → Hermes 把它塞进 system prompt → 模型看见」；
新链路只做到第一步，后两步没了。而两处文档仍按旧语义称呼它：`ARCHITECTURE.md:37` 写
"`memories/MEMORY.md`  L1 主记忆（§ 分隔，配额 3000 / 触发线 2550）"、"L1 主记忆"这个"主"字
在 Hermes 语境里就是"进提示词的那一层"；`README.md` §成本 也只算 catalog 的 644 字符。
**没有任何一处文档说"L1 不注入"——这正是它没被发现的原因。**

实测（`$env:TEMP\eco-delta-*`，同一 root 连续两轮）：

```
BEFORE: {... "items":[{"id":"mem-20261030-97c22169", "line":"DELTA 记忆条目：部署脚本放在 D:/work/tools", ...}]}
(手工把 occurrences 改成 9 / session_count 改成 5，跑 gate 2 → promoted 1 条，MEMORY.md 写出 36 字符)
AFTER : {... 与 BEFORE 逐字节相同 ...}
目录文本完全没变（门②对模型可见面零影响）: True
```

三条独立的负结果，指向同一件事：

| 探测 | 结果 |
|---|---|
| `catalog --scope global`（插件唯一注入源） | 只列 `detail/` 里的条目，**从不读 `MEMORY.md`** |
| `search "周报"`（只存在于 L1 的条目） | `count: 0` |
| `load "L1-独有条目：…"` | `{"ok":false,"error":"not-found"}` |
| 生产根 `%LOCALAPPDATA%\hermes\memories\MEMORY.md`（3911 字节，真实内容） | 在 dsh 里**没有任何代码路径会读它** |

**会话日志层面的实证（比读代码更硬）**：遍历 `~/.dsh/sessions/` 下 59 个真实会话的
`session*.jsonl.zstd`（排除当前会话），找 `MEMORY.md` 里三条独有串
（"QQ bot双端部署" / "四季平均云量" / "ConvLSTM重训"）：

```
命中文件 2 个 → 全部落在 tool/result（agent 自己 cat 了该文件）
               与 assistant/message（agent 在回话里复述）
user/message / system/message / request/header 类事件里：0 次
```

**也就是说：`MEMORY.md` 的内容在真实 dsh 会话历史里出现过的每一次，都是"agent 主动去读文件"，
没有一次是宿主/插件注入的。** 这不是推断，是 59 个会话的日志统计。

后果分三层，一层比一层难看：

1. **功能层**：门② 的"提升 L2→L1"、门③ 的"画像进 USER.md"，产出的东西模型永远看不到。
   `README.md` 成本表里"目录段 ≤644 字符，走缓存"说的是 catalog，与 L1 无关 —— 也就是说
   **我们真正的常驻记忆面只有 600 字符的目录摘要**，3000 字符的 L1 配额是个装饰。
   （对照：Hermes 那边 `memory_char_limit: 3000` + `user_char_limit: 1500` 是**真的进提示词**的 4500 字符。）
2. **判据层**：这正是 C2「无消费者的字段/接口 = 断链」的字面违反。而且它躲过了 167 条测试，
   因为所有测试都在验"门跑了吗、写出去了吗"，没有一条验"**下一轮模型能不能看见**"。
3. **归因层**：它和 v3.2.2 修的 H1（门②③④ 结构性从不运行）是**同一后果、不同成因** ——
   修好 H1 让门跑起来了，但门跑出来的东西没有出口，等于从"没跑"升级成"跑了白跑"。
   这也解释了为什么门② 在真实库上 promote 恒为 0 的历史数据没人觉得奇怪：**即使 promote 成功，也没有任何东西会变。**

**修法（二选一，都不是调参）**：
- A（推荐）：把 L1 纳入注入面 —— 目录段 = `MEMORY.md` 前 N 字符 + 本圈目录尾部，两条都有读者；
- B：承认 L1 是"人看的摘要"，删掉门② 的 L1 语义，只留"关系统计"，避免继续维护一个假层。
  无论选哪条，都要补一条消费端断言：**"门② promote 之后，`catalog` 文本必须变"**，跑在旧代码上必须是红的。

**生产现状（不是理论风险）**：

| profile | 挂的插件 | 数据根 | L1 有没有注入 |
|---|---|---|---|
| `desktop`（日常在用） | `eco-note-dsh-cordis`（v3.1 兼容版，`link:C:/Users/qy160/dsh-memory-ecology/...`） | `C:/Users/qy160/AppData/Local/hermes` | **没有**。它的注入器 `integrations/dsh/package/python/eco_note_dsh_context.py` 只扫会话里的工具报错、注入 1–3 条经验（≤1200 字符），**从不读 `MEMORY.md`/`USER.md`** |
| `eco-proto`（隔离验证） | `eco-memory`（本仓库 v3.2.2 插件） | `D:/work/_eco_proto_root` | **没有**（`detail: 3`，同一断点） |
| 生产 dsh 根 | — | `%LOCALAPPDATA%/dsh/memory-eco` | `detail: 0`，四门全 `dead`/`idle-spin`（`health` 实跑），等于空库 |

也就是说：**两条 dsh 通道（旧的 eco-note、新的 eco-memory）都不注入 L1**。
Hermes 侧的 3911 字节 `MEMORY.md` / 3031 字节 `USER.md` 是**真的进提示词**的（`system_prompt.py:527-532`），
但那是 qqbot 那个宿主，跟 dsh 会话无关 —— 迁移之后这部分记忆对 dsh **彻底静默**。

### 3.2 【中】没有"人和约"的保留区：L1 里放不住不可牺牲的东西

v17 把配额切成两半：**事 2048 字节 / 人+约 2048 字节，且"人和约永不自动删，只缩不消失"**。
我们这边 `store.MEMORY_QUOTA = 3000`，`_extrude()` 的优先级是"非高价值同源 → 非高价值历史日期 → 非高价值靠后"，
**没有任何 `pinned` 概念** —— 一条"我的身份/长期约定"与一条"v3.2.2 改了五个 bug"在挤出排序里地位相同，
前者更老，反而**更先被挤出去**（我们的排序语义刻意是"越老越先挤"，见 `gates.py:452-455`）。

这在 v17 的框架里是不可想象的：它的第一段就写"桌面页一半给人约"。而我们的体系里"人"只活在
门③ 的 USER.md 候选里，配额 1500，水位 90% 就停手 —— 也没有保留区。

**建议**：给 detail frontmatter 加 `pin: true`（或 `kind: identity|convention`），
在 `_extrude()` 里与 `protect` 同级豁免、在门④ 里永不降级，并补断言"pin 条目在 10 轮挤出的极端配额下仍在 L1"。
这条我们的 C4（可回滚）也满足：pin 只是标记，随时可解除。

### 3.3 【中】"唯一写者"只是一句口号：没有跨进程互斥

`README.md:28` 声称"唯一写者：一个数据根只允许一个执行方跑门"。实际：
- `append_line` 有 `msvcrt.locking` 旁路锁（只保护**单行追加**）；
- `gates.quota()` 的"读 MEMORY.md → 改 → `write_atomic` 写回"**没有任何锁**；
- 插件侧 `serialize()` 只串行化**本进程内**的任务；
- CLI 可以被人、观测舱、插件、计划任务同时调起。

实测：两个进程同时 `gate 1` → 都成功，产出 3 条、无重复（因为门① 是幂等 + 指纹去重，**运气好**）。
但门② 的读改写不是幂等的：两个进程各读到旧 L1、各写回自己的版本，**后写的整份覆盖先写的**，
被覆盖掉的那次 promote/extrude 不会留任何痕迹（账本两份都有，数据只有一份）。

v17 的 `nightly.lock` 给了三个可直接抄的细节：
1. **锁文件内容写"当前时间和进程号"** —— 死锁时可判读是谁；
2. **存在但不到 30 分钟 → 直接退出并打印"另一班在跑"**（不是排队等）；
3. **超过 30 分钟视为死锁，删掉重来；干完删锁。**

我们需要的不是它的实现，而是它的**语义**：`gate`/`maintain` 入口加一把进程级锁，
并让 `health` 能报"上一次门是被锁挡住的"（否则又是静默失败，违反 C3）。

### 3.4 【中】三本账我们只有一本：没有日档 / 总本 / 长期

v17 的书架是 `日档（每天一份摘要）/ 总本（全文导出）/ 长期（只写"我变了什么"）`。
我们只有 `detail/`（原子事实）+ `eco.db`（动作流水）。**没有时间线，没有叙事，没有"这周发生了什么"。**

这不是锦上添花，它影响两类查询：
- "我上次是怎么解决这个问题的" —— 需要**事件序列**，`detail` 是一条条孤立事实，`search` 按词面命中，拼不出经过；
- "我这个月改了哪些判断" —— 需要**变更史**，我们的 `supersede()` 只在单条 frontmatter 里留
  `superseded_by/reason/at`，跨条目的整体漂移不可见。

而**能力其实只差一步**：`measure.py` 已经在流式解 dsh 会话日志（`session*.jsonl.zstd`）了，
现在只用来数注入成本。同一份数据按天归并落 `日档`、按条抽 `user/message + assistant/message` 落 `总本`，
就是 v17 的第 13 步。差别只在"**要不要把读到的内容持久化**"。

注意红线：`总本` 是**全文导出**，一旦落盘就是一份完整的会话副本。v17 的处置是"保留最近 30 天，
更早的 gzip 进 `归档/`，原文件删掉"。我们若做，必须改成"**gzip 归档、永不删原件**"（红线 1），
并明确它落在哪个圈 —— 全文导出跨圈就是 §3.5 的泄漏放大器。

### 3.5 【提示】v17 没有"圈"：单文件全局共享

v17 的桌面页、日档、总本全是单份、全局。对单人单机没问题；对我们这套"多项目 + 多会话 + 有权密"
的场景，等于把我们 S2/S3 那类跨圈泄漏**内建**进去。反向看：**这正是我们复杂度的唯一正当理由**，
也说明我们的定位必须写清（见 §4.2）。

## 4. 战略层面的实际意义

### 4.1 交付形态：它的产品是"一段提示词"，我们的产品是"一个工程"

v17 的用法只有一句：**"新开一个对话，把方框里那段整段贴给 DSH"**。零安装、零依赖、跨机器、可复制传播。
我们的安装是 `dsh plugin add link:D:/work/...` + Python 核心 + 测试套件。

这不只是"谁更容易推广"，它改变了**失败的样子**：
- 它的失败是"模型今晚偷懒了" → 用户能感知（桌面页没更新）→ 用户的补充第 1 条就是"记得提醒 dsh 问【记忆更新了没】"；
- 我们的失败是"事件处理器抛异常但只写了 debug 日志" → 用户完全无感（这就是 H1，藏了两个月）。

**结论**：我们应该同时产出**提示词形态**的入口 —— 一份"部署提示词/技能卡"，粘贴即用，
内部仍然调 `python -m memory_ecology`（保证机制不变），而不是要求用户先 clone 一个仓库。
提示词里保留它最有效的四条自报（开场/补检/翻本子/收尾），因为那是**唯一能让人眼发现"机器在说谎"的接口**。

### 4.2 复杂度分层：它证明"小规模下文件+纪律够用"

v17 的规模假设是"几百条、一个人、一年"。我们的 202 条中文件名、238 篇 detail、跨圈隔离需求，
才让"指纹去重 / 取代链 / 状态机 / 唯一写者 / 回滚"这些复杂度**回本**。
写 README 时应该直接承认：**单人单机、条目 <500、无隔离需求 → 用 v17 那套就够，别上我们这套。**
把适用边界写在最前面，比多写十条特性更能建立信任。

### 4.3 成本架构：它每天重写"桌面页"而不毁缓存，我们的目录段一改就全废

这是本轮唯一一条**有我们自己的实测数字**、且可以直接改设计的启示。

先纠正 v17 的一个前提：**"桌面页每轮自动读"在 dsh 里不成立**。`dsh-agent-instructions` 的说明原文
（`README.zh.md:12`）："没有文件 watcher —— 外部编辑会在下一次成功的文件系统 touch 时，
或恢复后的会话对账其基线时变得可见。"也就是说它的记忆更新要**下一次新会话**（或某个 fs touch）才生效，
不是每轮。这不影响方案可用，但影响对"实时性"的预期。

成本上它做对了一件事：

- 它的记忆段进的是 `AGENTS.md`，而 `dsh-agent-instructions` 把指令上下文作为**普通 `user/message`** 注入
  （`README.zh.md:84`："基线消息与刷新消息都是普通的带来源 `user/message` 事件"；
  KV 影响段 `:153`："仅追加，位于现有可复用前缀之后"）。**所以它的日更不毁 KV cache。**
- 我们的目录段是 `ctx.systemPrompt.section(order=9100)`，**在前缀里**，而且 `text` 是个**活函数**
  （`plugin/index.js:457` `text: () => state.catalogText`）—— 每次装配都重新取值。
  只要 `state.catalogText` 在会话中途被换掉，同一会话的下一轮就是新前缀。

中途被换掉的路是存在的（都在 `plugin/index.js`）：`agent/created`（含 `resume`）→ `syncView`；
`subagent` 在同进程建 agent → 同样触发；维护里 promote 成功 → `syncView({audit:true})`。
实测过一次前缀改写的代价：**0.29 元**（`上下文成本模型-注入与裁切-20261029.md` §1）。
注：门② 的 promote 只写 `MEMORY.md`、不动 `detail`，所以它目前**不会**改 catalog（见 §3.1 的讽刺之处）；
真正的触发源是别的会话新整合进来的条目 + resume/子代理。

**落点**：把"可能会变的那一段"从 `systemPrompt.section` 挪到 append-only 的 `user/message`，
`systemPrompt` 里只留"一会话绝对不变"的部分（本机 profile 名、圈名这类）。
不改语义，只改开销的形状：从"改一次前缀 0.29 元"变成"追加 n token × miss 价"。
目录 600 字符 ≈ 400–600 token ≈ **0.001 元/次**，两个数量级。
顺带把 `ARCHITECTURE.md:180` 那句"≤1 次/会话（内容不变就不重建）"改成诚实版：
**代码没有"一会话只算一次"的守卫，只是"内容没变就不重建"**。

### 4.4 成本数字交叉验证（顺手核一下它的说法）

它的补充第 2 条：每天一次更新花 3–5 分（按"分钱"理解 ≈ 0.03–0.05 元），日常对话额外 ≈ 一分钱的十分之一（0.001 元）。
按我们的实测口径：目录 600 字符 ≈ 400 token，首次 miss 2 元/M = 0.0008 元，之后每轮 hit 0.04 元/M ≈ 0.000016 元，
100 轮约 **0.002 元**。同量级 —— 两套设计在"钱"上都不是问题。
**所以成本不是选型依据，失败模式才是。**

## 5. 不可照抄的地方（以及为什么）

| v17 的做法 | 为什么我们不抄 |
|---|---|
| 全靠模型每晚按提示词执行 | 违反 C6「不依赖纪律」。作者自己的补充第 1 条就是证据："dsh 有时特别懒……需要你提醒"。**需要人提醒的机制不是机制。** |
| 掷骰子（3% / 1%）决定升层 | 概率不可断言（C5）、不可回滚（C4）。我们已用"确定性 protect + 30 天冷却 + 撤销本轮提升"解决同一问题（防震荡）。 |
| 事 30 天"删" | 物理删除。我们红线 1 在代码层禁用 unlink，只做状态迁移 + 隔离区。它对人/约承诺不删，对"事"是假的不删。 |
| `add` 只发 id、不去重 | 同一件事记十遍就是十行。我们的门① 指纹（**含 scope**）+ 同源合并 + 取代链正是为此。 |
| 单份桌面页，无圈 | 跨项目泄漏。我们有 `circles.json` 最长前缀路由 + `scope` 隔离断言。 |
| 五天/四柜层数在文中不一致（开头"四个柜子"，nightly 写"第一~第五层"） | 提示词即规格，没有测试就一定会漂。这正是我们 `test_config_keys_have_consumers` 那类断言存在的理由。 |

1. **修 L1 孤儿（§3.1）** —— 让 `MEMORY.md` 进目录注入，或承认它只是人看的摘要并砍掉门② 的 L1 语义。

   是否真的出现在（本圈）注入文本里；对不上就 `warn`。这条检查在我们现在的代码上**立刻会报红**，说明它有用。
3. **给 `gate`/`maintain` 加进程级锁（§3.3）** —— 抄它的三条语义（写 pid+时间 / 30 分钟内直接退出 / 超时判死锁），

次要（按价值排序）：pin 保留区（§3.2）→ 目录段从前缀挪到 append-only（§4.3）→ 日档/长期（§3.4）→ 提示词形态入口（§4.1）。
